## Зачем форк

Штатная интеграция работает и уже даёт бо́льшую часть нужных сущностей, но на нашем железе
есть дефекты, которые мешают строить достоверную аналитику в Grafana:

1. **Сетевая мощность не читается вообще.** Регистр 340 объявлен в схеме, но в опрос не попадает;
   202/204/205/206 (ток/P/VA сети и заряд от сети) на этом инверторе всегда 0. Следствие — модель
   «додумывает» импорт из баланса, и появляется фантомный `Grid to Battery Power`
   (пример: нагрузка 409 Вт, PV 850 Вт, заряд АКБ 560 Вт от PV → HA показывает 119 Вт «из сети в АКБ»).
2. **Логика потоков** ограничивает `PV → АКБ` остатком PV после дома (441 вместо измеренных 560)
   и не учитывает запрет заряда от сети (настройка 641).
3. Часть полезных регистров (плечи L1/L2, внешний CT 326–327, коды ошибок/предупреждений с
   расшифровкой, PV1/PV2) не выведена в сущности.

Цель форка — **одна точка опроса (HA)** с полным и честным набором измерений, без второго
процесса и без конфликта за единственный сеанс донгла.

  Скрипт — инструмент разведки и проверки, **не второй опросчик**.

## Как начинать работу

1. Прочитать `docs/fork/agent-brief.md` целиком (там правила, которые нельзя нарушать).
2. Согласовать объём по `docs/fork/requirements.md` (владелец утверждает пункты).
3. Ветка от `main` → изменение → `python3 tools/quality_gate.py` → коммит → PR (сначала в свой
   форк, upstream — только для универсальных исправлений).
