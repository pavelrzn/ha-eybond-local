Поведение донгла (наблюдения):
- сам перезагружается примерно каждые 12 ч (около 02:00 и 14:00 MSK) — плановый разрыв ~2–10 мин;
- частая переподключка (каждые 15 с) **роняет его**: уходит из сети, восстановление только
  полным обесточиванием инвертора;
- типовой отказ: **UDP-приглашение отвечает (`rsp>server=N`), но TCP не открывается** —
  признак залипшей/занятой сессии. Не долбить: одна попытка, затем доклад владельцу;
- релевантные регистры: 198 (power flow bitmap), 201 (режим), 202–206 (сеть), 226–231 (инвертор),
  252–256 (выход), 277–281 (АКБ), 302–305 (PV), 326–327 (внешний CT, Long), 338–345 (сеть/инвертор L1),

## 2. Архитектура интеграции (по upstream-докам)

```
transport → payload → driver → profile → register schema → HA entities
```

- Максимально много логики — **в JSON**: `protocol_catalogs/register_schemas/**` (разметка чтения,
  модели, оверлеи), `protocol_catalogs/profiles/**` (капабилити, пресеты, условия).
- Python-драйвер — тонкий: детект, чтение, запись, процедурные производные
  (`drivers/smg.py`, `canonical_telemetry.py`, `derived_energy.py`).
- HA-сущности — только представление.
- Схемы наследуются: `base.json` → `protocols/communication_protocol_3_10.json` → `..._4.json`;
  слияние по ключу, `spec_set_removals` вырезает унаследованные ключи.
- Модель-оверлей нашего инвертора: `register_schemas/modbus_smg/models/anenji_anj_11kw_48v_wifi_p.json`
  (только `extends`, без своих правок).

## 3. Известные дефекты на нашем железе (проверено 2026-10-19)

### 3.1. `grid_power` не читается, отсюда фантомный `grid_to_battery`
- В схеме `communication_protocol_3_10.json` ключ `grid_power` объявлен дважды: `live` → 204
  (удалён из live через `spec_set_removals`) и `aux_config` → **340**.
- По debug-логу HA реально опрашиваются: `100+10, 171+1, 184+1, 198+34, 252+5, 277+5, 302+4,
  338+1, 342+1, 346+1, 351+3, 389+3, 600+57, 677+18, 696+9, 707+1, 709+1`.
  **Регистр 340 в списке отсутствует** (338 и 342 читаются по одиночке, значит 339–341/343–345
  в наборе нет).
- Следствие: `grid_power = None` → в `canonical_telemetry._compute_flow_split` срабатывает
  ветка «сеть присутствует (по 338), но мощность сети неизвестна» → импорт оценивается балансом
  `load + battery_charge − pv − battery_discharge`.
- Живой пример: load 409, pv 850, pv_charging 560, battery 560 → инференс 119 Вт → эти 119 Вт
  попадают в `Grid to Battery`, хотя заряд идёт от PV и заряд от сети запрещён настройкой 641.
- Дополнительно: регистры 202/204/205/206/228 на этом инверторе **всегда 0** (проверено на 5448
  строках CSV 16.09–06.10, включая 1032 строки «нет PV, нагрузка >150 Вт, АКБ не заряжается»).
  То есть даже если начать читать 204 — значения не будет; 340 на этой прошивке тоже не заполняется.
  Реальная сетевая мощность появится только с внешним CT (326–327 при 686=1) или внешним счётчиком.

### 3.2. Логика потоков занижает `PV → АКБ`
- `pv_to_battery` ограничивается остатком PV после дома, а не измеренным `pv_charging_power` (303):
  тот же пример даёт 441 Вт вместо 560.

### 3.3. Не выведены в сущности
- плечи L1/L2, PV1/PV2, внешний CT, коды ошибок/предупреждений с расшифровкой битов,
  полный набор настроек. `TODO/проверить`: часть может быть в disabled-by-default диагностике.

### 3.4. Ложный путь, который уже проверен и отвергнут
- Патч «запретить инференцию импорта в АКБ» ломает **7 существующих тестов**: для протоколов,
  где регистра сетевой мощности нет вообще (например `eybond_g_ascii`), апстрим намеренно
  разрешает такую инференцию, и это зафиксировано тестами. Поведение менять нельзя без
  согласования с upstream.

## 4. Правила работы (нарушать нельзя)

1. **Один опросчик.** HA и ручной сборщик одновременно не запускать: донгл один сеанс.
2. **Одна попытка сессии на запрос.** Не получилось — стоп и доклад. Ретраи внутри одной
   сессии (повтор блока) допустимы.
3. **Только чтение по умолчанию.** Никаких записей в инвертор/донгл без явного разрешения владельца
   (FC=3 и Modbus 0x06/0x10 запрещены в инструментах форка).
4. **Сначала анализ, потом фикс.** При багах — причина, потом правка (правило владельца).
5. **План до работы.** Перед доработками — план и уточняющие вопросы; объём согласуется.
6. **Данные — в JSON, код — минимальный.** Следовать `CONTRIBUTING.md` upstream.
7. **Секреты не коммитить.** Дампы донгла содержат SSID и Wi-Fi-пароль.
8. **Не менять upstream-файлы без нужды.** Свои документы — только `docs/fork/**`,
   изменения кода — отдельными ветками (меньше конфликтов при мерже upstream).
9. **Даты в доках.** Любой существенный пункт помечать `[ГГГГ-ММ-ДД]`, чтобы читатель оценивал свежесть.

## 5. Как проверять изменения

- Канонический прогон: `python3 tools/quality_gate.py` (внутри — `unittest discover -s tests`).
- Зависимости для локального прогона: `requirements-test.txt` (нужны `aiohttp`, `voluptuous`;
  HA не устанавливается — тесты используют фейковые пакеты `homeassistant.*`).
- CI-версия Python: 3.12 (`TODO/проверить` — сейчас в CI; локально код требует 3.10+ из-за `X | Y`).
- Поведение потоков проверяется в `tests/test_canonical_telemetry.py`; при правке
  `canonical_telemetry.py` — обязательный регрессионный тест с нашими числами
  (load/pv/pv_charging/battery + отсутствующий grid_power).
- После установки в HA: смотреть debug-лог (`… [custom_components.eybond_local.collector.transport]
  TX/RX …`) — он показывает фактические регистры опроса; это самый быстрый способ убедиться,
  что новый регистр действительно читается.
